# 决策记录：采用 GPU 球体地图渲染作为长期方向

## 状态

- 日期：2026-05-01
- 决策状态：已采纳
- 关联需求：`docs/requirements/2026-05-01-gpu-globe-boundary-renderer.md`
- 关联任务：`tasks/in-progress/2026-05-01-gpu-globe-boundary-renderer.md`

## 决策

采用 GPU 球体地图渲染作为长期地图架构方向。短期使用 React Three Fiber 接入新的 globe renderer，逐步从当前 Pixi 2D 投影渲染迁移到球面顶点、GPU 旋转、LOD 数据和 GPU picking 的路线。

## 原因

- 高精度边界和流畅旋转天然冲突于“运行时全量 GeoJSON 主线程投影”。
- GPU 球体方案可以把拖拽旋转变成矩阵变换，避免每帧在 JS 中重投影全部经纬度点。
- 后续可自然支持球面边界、轨道层、热力层、前线层、区域高亮和离屏 picking。
- 游戏的地图体验是核心玩法界面，长期掌握渲染管线比完全依赖通用地图引擎更合适。

## 被比较方案

| 方案 | 结果 | 原因 |
|---|---|---|
| 继续优化 Pixi + d3 投影 | 不作为长期主线 | 可短期止血，但无法根治每次旋转重投影和复杂 Graphics 重绘 |
| MapLibre GL JS | 保留中期备选 | 矢量瓦片能力成熟，但游戏化球体、玩法图层和自定义交互会受地图引擎边界限制 |
| PMTiles/MVT + Pixi | 中期数据管线方向 | 适合按需加载，但仍需渲染层配合 |
| GPU 球体 + 自有渲染层 | 采纳 | 最符合高精度边界、球体旋转、游戏图层和长期扩展目标 |

## 迁移原则

- 分阶段推进，不一次性删除 Pixi 地图。
- 规则层和游戏状态继续保持框架无关。
- 渲染层作为适配器，不把游戏规则写入 Three/R3F 组件。
- 先做边界线和拖拽流畅性，再迁移填充、hover、前线、链接、图标、天气和动画。
- 数据管线先复用 GeoJSON，后续再转 LOD / PMTiles / 自定义二进制。

## 后续动作

1. 新增 GPU globe 渲染组件和球面几何工具。
2. 接入 GameMap，保留 Pixi fallback。
3. 通过构建和基础浏览器验证确认场景可见、非空、可拖拽。
4. 后续补 LOD、GPU picking、区域填充与玩法图层迁移。
